📚 What is Version Control?

📚

Definition

Version control is a system that records changes to a file or set of files over time so that you can recall specific versions later.

⏰

Why It Matters

Think of it as a time machine for your code - you can go back to any point in your project's history.

Types of Version Control Systems

💾

Local Version Control

Simple database that keeps all the changes to files under revision control

Example: RCS (Revision Control System)
🏢

Centralized Version Control

Single server contains all versioned files, clients check out files from central place

Example: Subversion (SVN), CVS
🌐

Distributed Version Control

Full mirror of the repository, including its full history

Example: Git, Mercurial

🔬 Why Version Control Matters in Research

🔬

Reproducibility

Track exactly what code and data produced your results, making research reproducible and verifiable.

🔄

Experiment Safely

Try new approaches without losing your working code. Always know you can go back to a working version.

👥

Collaboration

Work with others on the same project without conflicts. See who changed what and when.

📊

Documentation

Every change is documented with messages explaining what and why, creating a project history.

🌍

Real-World Example: COVID-19 Modeling

During the COVID-19 pandemic, researchers worldwide collaborated on epidemiological models. Version control allowed them to:

📈 Track parameter changes as new data emerged
🤝 Collaborate across institutions without conflicts
🔄 Reproduce results from specific dates
💡 Share improvements and bug fixes

📖 The Git Parable: Understanding Snapshots

Let's understand Git's core concept through a simple analogy. Think of Git as a photographer taking snapshots of your project at different points in time.

Why Snapshots Matter

Git's snapshot approach makes it incredibly powerful for:

⚡

Fast Operations

Jump to any commit instantly, regardless of how old it is

🔒

Data Integrity

Each commit is cryptographically secure and tamper-proof

🔄

Easy Branching

Create new branches by simply pointing to any commit

📊

Efficient Storage

Smart compression stores only what's changed between versions

Git Basics: Understanding the Fundamentals

What is Git?

Git is a distributed version control system that tracks changes in your files over time. Think of it as a time machine for your code that remembers every change you make.

Key Git Concepts

Repository

A directory that contains your project and the entire history of changes. The .git folder stores all the version control information.

Commit

A snapshot of your project at a specific point in time. Each commit has a unique identifier and a message explaining what changed.

Branch

A separate line of development that allows you to work on features independently without affecting the main codebase.

Remote

A copy of your repository stored on another computer (like GitHub) that allows collaboration and backup.

Core Git Philosophy

📸 Snapshots, Not Differences

Git thinks of its data more like a series of snapshots of a miniature filesystem.

v1
v2
v3

🔒 Nearly Every Operation is Local

Most operations in Git only need local files and resources to operate.

✅ Git Has Integrity

Everything in Git is checksummed before it's stored using SHA-1 hash.

➕ Git Generally Only Adds Data

When you do actions in Git, nearly all of them only add data to the Git database.

Hands-on Practice: Your First Git Repository

Exercise 1: Initialize a Git Repository

Let's create your first Git repository and make your first commit!

Step 1: Create a Project Directory

Terminal Commands 
# Create a new directory for your project
mkdir my-first-project
cd my-first-project

# Verify you're in the right place
pwd

Step 2: Initialize Git Repository

Git Command 
# Initialize a new Git repository
git init

# Check the status
git status

This command creates a new Git repository in your current directory. The .git folder is created to store all version control information.

Step 3: Create Your First File

Create a README file 
# Create a README file
echo "# My First Project" > README.md

# Check what files exist
ls -la

# Check Git status again
git status

Now you have a file that Git can track. Notice how git status shows the README.md file as "untracked".

Step 4: Stage and Commit

Stage and commit your changes 
# Stage the README file for commit
git add README.md

# Check status again
git status

# Make your first commit
git commit -m "Initial commit: Add README file"

# Check the commit history
git log

Congratulations! You've made your first commit. The -m flag adds a message explaining what this commit does.

Understanding Git Status and History

Git Status: Your Project's Health Check

The git status command is your best friend. It tells you exactly what's happening in your repository.

Clean Working Directory

On branch main
nothing to commit, working tree clean

This means all your changes have been committed and there are no uncommitted modifications.

Modified Files

On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   README.md

no changes added to commit (use "git add" and/or "git commit -a")

This shows you have modified files that haven't been staged or committed yet.

Staged Changes

On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        new file:   analysis.R

Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   README.md

This shows you have both staged files ready to commit and unstaged modifications.

Git Log: Your Project's Timeline

The git log command shows you the history of all commits in your repository.

View commit history 
# View full commit history
git log

# View compact history (one line per commit)
git log --oneline

# View history with file changes
git log --stat

# View history with graph (useful for branches)
git log --graph --oneline --all

Example Output

commit abc1234 (HEAD -> main)
Author: Your Name 
Date:   Mon Mar 25 10:30:00 2025 +0000

    Add data analysis script

commit def5678
Author: Your Name 
Date:   Mon Mar 25 09:15:00 2025 +0000

    Initial commit: Add README file

Each commit shows a unique identifier (hash), author, date, and commit message.

Common Pitfalls & How to Avoid Them

❌

Forgetting to Commit

Working for hours without committing can lead to lost work

Solution: Commit frequently with meaningful messages
❌

Vague Commit Messages

"Fixed stuff" doesn't help future you or collaborators

Solution: Use descriptive messages like "Fix data loading error in analysis.R"
❌

Committing Large Files

Adding data files, images, or binaries can bloat your repository

Solution: Use .gitignore for large files, keep data separate
❌

Not Checking Status

Committing without knowing what's changed can lead to mistakes

Solution: Always run git status before committing

Best Practices for Commit Messages

✍️

Writing Good Commit Messages

Good commit messages make your project history readable and useful for future you and collaborators.

✅

Do This

  • Use present tense ("Add feature" not "Added feature")
  • Start with a verb ("Fix bug", "Update documentation")
  • Be specific and descriptive
  • Keep first line under 50 characters
  • Use body for longer explanations
❌

Avoid This

  • Vague messages like "Fix stuff" or "Update"
  • Past tense ("Fixed bug", "Updated docs")
  • Messages that don't explain what changed
  • Very long first lines
  • Emotional language ("Fix this stupid bug")

Good vs. Bad Commit Messages

See the difference between effective and ineffective commit messages

✅
Good Examples
git commit -m "Add SIR model parameters" Clear, specific, present tense
git commit -m "Fix data loading error in analysis.R" Specific file and issue mentioned
git commit -m "Update README with installation steps" Clear what was updated and why
git commit -m "Refactor model fitting function for clarity" Explains the purpose of the change
❌
Bad Examples
git commit -m "stuff" Too vague, no information
git commit -m "Fixed bug" Past tense, not specific
git commit -m "Update" No context about what was updated
git commit -m "This is a very long commit message that goes on and on and doesn't follow the 50 character rule" Way too long, violates best practices

📚 Quick Reference: Essential Git Commands

Getting Started

git init Initialize a new Git repository
git clone Clone a repository from remote source
git status Check repository status

Making Changes

git add Stage files for commit
git commit -m "message" Commit staged changes
git diff View unstaged changes

Viewing History

git log View commit history
git log --oneline Compact commit history
git show View specific commit details

Undoing Changes

git restore Discard unstaged changes
git reset HEAD~1 Undo last commit (keep changes)
git revert Create new commit that undoes changes
